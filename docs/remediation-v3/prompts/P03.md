# P03 — Multi-Symbol Matching

## Objective
Bring multi-symbol matching to production-grade correctness in the real runtime path.

## Current Problem
Single hardcoded matcher in the runtime (PB-04); MarketRegistry unused in production.

## Root Cause
Implementation exists in an architecturally correct package but the runtime does not use it,
or the implementation itself is non-standard. See docs/remediation-v3/AUDIT.md for evidence.

## Affected Files / Modules
apps/matching-engine/main.go:79, apps/matching-engine/engine/oms_router.go, engine/market_registry.go

## Architecture Requirements
Single owner, single source of truth, single runtime path for every operation in scope.
No parallel or dead implementation may remain after this Part.

## Technical Requirements
OMSRouter resolves the matcher from MarketRegistry per order symbol. No NewMatcher call outside the registry in non-test code.

## Security Requirements
Fail closed on missing configuration or secrets. No mock, fallback or hardcoded credential
reachable from a production build.

## Financial Requirements
No financial mutation without a ledger trail, an idempotency key and deterministic rounding.

## Database Requirements
Schema changes ship as migrations in packages/database/migrations.go with the constraints the
invariants rely on (UNIQUE, FK, NOT NULL, CHECK).

## API Requirements
Contract changes are versioned and reflected in handlers, WebSocket payloads and the frontend client.

## Implementation Steps
1. Inspect current call graph and list every call site.
2. Implement the correct behaviour in the owning package.
3. Wire it into the runtime and delete or redirect the previous path.
4. Add migrations if the schema changes.
5. Add tests, including failure scenarios.
6. Run `go build ./...`, `go vet ./...`, `go test ./...` and record output.
7. Commit with a real source diff.

## Tests
BTC order never touches ETH book; per-market price-time priority/FIFO; concurrent multi-market determinism.

## Failure Scenarios
Crash, restart, replay, duplicate delivery, concurrency, missing configuration, invalid input.

## Acceptance Criteria
- Behaviour proven by executed tests, not by documentation.
- Runtime wiring verified by a call-path trace.
- No duplicate implementation of the same business operation.

## Definition of Done
Source code + runtime wiring + tests + executed test output + regression + documentation + commit.
